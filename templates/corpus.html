What I would do, in order

  1. Halve the index before adding anything to it. pgvector {{ (s.extensions or {}).get('vector', '') }} has halfvec: 16-bit floats, half the bytes, a recall loss measured elsewhere in the low tenths of a percent at 768 dimensions. {% if pr %}That takes the index from {{ pr.hnsw_gb }} GB to about {{ pr.halfvec_hnsw_gb }} GB, which is the difference between not fitting in {{ pr.ram_gb }} GB of RAM and fitting with room to grow.{% endif %} It is a re-index and a query-path change, not a re-embed, so it costs no model spend. Do this first, and measure recall on the frozen gold set on both sides of it.
  2. Decide the second field by CPC, and ingest citations with it. The corpus is not eight CPC groups of documents, it is those plus what they cite: that is how eight groups became {{ (snap.classifications[0].subclasses if snap.classifications else '700+') }} subclasses. A new field should be seeded the same way, and its size estimated from its CPC counts in BigQuery before a single row is pulled.
  3. Do not re-point the out-of-domain detector in the same change. It is calibrated against the eight seed groups. Widening the ingest is additive and safe; moving the field definition is a ranking change, and shipping both at once makes it impossible to say which one moved the numbers.
  4. Expect recall to fall before it rises. A bigger index at the same ef_search returns a shallower slice of a larger space, so the same query gets a worse neighbourhood. Budget for re-tuning the retrieval depth, and re-run the frozen gold set as the acceptance test rather than eyeballing a few searches.
  5. Cost the reading, not the corpus. A deep run reads three to four hundred documents in full whatever the corpus size, so a wider corpus does not by itself cost more per search: it changes which documents get read. The bill moves when the screen has more plausible candidates and the budget is raised to match.
