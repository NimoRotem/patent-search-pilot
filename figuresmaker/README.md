# Patent figures maker

<https://nimo.iptorch.com/figuresmaker/>

A draft goes in. A checked figure set comes out: SVG sheets sized and margined for filing, a PDF,
and a redline of the specification saying what the drawings require the text to say.

The whole thing rests on one decision. **Figures are structured data rendered deterministically,
not images generated by a model.** Compliance with 37 CFR 1.84 is a set of rules about geometry,
characters and lead lines, and you can only check a rule programmatically if you own the geometry,
the characters and the lead lines as data. So a model is never allowed to draw. It reads the
draft, it decides what the views are, and it fills in a schema whose every field is either a name
from a fixed library or a number that gets clamped. Everything after that is arithmetic.

---

## The pipeline

```
draft ──▶ sections ──▶ registry ──▶ claims ──▶ plan ──▶ scene ──▶ render ──▶ place ──▶ check
             │            │           │          │        │          │          │        │
          headings    numerals     features   figures  geometry   primitives  numerals  findings
                      + conflicts             (LLM)     (LLM)      in mm      lead lines  ──┐
                                                                                            │
                                       ◀────────── bounded retry, routed by stage ───────────┘
```

### 1. Ingest (`fm/ingest.py`)

Paste, a patent number, any link, a PDF or a `.docx`. A number or a Google Patents link resolves
to the published text.

The normaliser at the bottom of that module matters more than it looks. A published text layer
puts a space before every comma, breaks words across lines, and inserts a non-breaking space
inside `1 02`. Every one of those defeats the numeral regex, and a numeral the registry never sees
is an element that never reaches a drawing.

The HTML extractor is block-aware and keeps inline elements. Google Patents wraps every figure
reference in an inline `<figref>`; an extractor that takes only a block's direct text turns
"FIG. 1 is a block diagram of a system" into "is a block diagram of a system", the brief
description parses to nothing, and the figure set gets invented instead of read. There is a
regression test for exactly that.

### 2. Sections and claims (`fm/sections.py`, `fm/claims.py`)

Headings are matched only when they sit alone on a line, so "as stated in the summary above" does
not silently truncate the description. Claims are split on the punctuation patent claims actually
use, then a model corrects the cases where the punctuation lies.

A numeral belongs to a figure because it appears in a paragraph that is talking about that
figure, and a paragraph is talking about the last figure anybody named. Carrying that context
forward is what turns "housing 102" into "housing 102, shown in FIG. 1 and FIG. 3".

### 3. The registry (`fm/registry.py`)

The single source of truth. Built twice over: a regex first, because patent prose puts the
numeral immediately after the noun it names, then a model, because deciding that "the housing",
"said housing" and "the outer housing" are one term is a judgement.

Conflicts are found **before anything is drawn**, and each is reported against whoever can fix it:

| code | what | authority |
|---|---|---|
| `numeral_two_terms` | one character, two different parts | 37 CFR 1.84(p)(5) |
| `term_two_numerals` | one part, two characters | 37 CFR 1.84(p)(5) |
| `numeral_no_figure` | a character no paragraph ties to a view | 37 CFR 1.84(p)(4) |
| `figure_never_discussed` | a view the brief description promises and nothing describes | 37 CFR 1.84(p)(4) |
| `element_unnumbered` | a part described and never numbered, with a free numeral suggested | 37 CFR 1.84(p)(4) |

### 4. The plan (`fm/plan.py`)

If the draft has a **Brief Description of the Drawings**, it is authoritative: those figures, those
labels, those kinds. Inventing a different set would be a change to the specification.

If it has none, figures are generated so that every element of every independent claim appears in
at least one of them, because 37 CFR 1.83(a) requires the drawing to show every feature the claims
specify, and a proposed brief description is written back for the author to paste in.

### 5. Scenes and rendering (`fm/render/`)

One schema per figure type, and the renderer owns everything after it.

| kind | how it is drawn |
|---|---|
| `block_diagram`, `flowchart` | a graph, laid out by Graphviz `-Tjson`, drawn from the coordinates |
| `sequence` | deterministic lifeline layout |
| `perspective`, `exploded`, `cross_section` | placed solid primitives, orthographic projection, exact hidden-line removal |
| `ui_screen` | a wireframe tree, laid out by arithmetic here, not by the model |

**Hidden-line removal is exact, not sampled.** An edge and a triangle both project to the sheet as
straight things, and the depth of each is affine in position, so the interval of the edge the
triangle covers, and the part of that interval where the triangle is nearer the eye, are both
solved rather than tested at points. A sampled test drops the last half millimetre of a line at
every crossing, and a hundred of those is what makes a generated drawing look generated.

**Silhouettes are found without reference to winding order.** On a curved surface the outline you
see is where the surface folds away, and there both faces meeting at the fold project to the same
side of it. That test needs no normals, which keeps forty different mesh builders from having to
agree about handedness.

**Sections really cut.** The mesh is clipped against the plane, the cut segments are chained into
closed loops, the loops are capped so you cannot see through the hole, and the caps are hatched
with oblique parallel lines per 37 CFR 1.84(h)(3), a different angle per part, and the same angle
for the same part in every view.

`fm/appearance.py` is why a housing looks like a housing in FIG. 4 as well as FIG. 1: the first
figure that draws a part decides what it is, and every later figure gets that decision as a
constraint.

### 6. Placement (`fm/render/leaders.py`)

A separate stage, because a renderer that places its own numerals places them where they were
convenient to compute, and the rules are not about convenience.

Every numeral has anchors, which are points genuinely on lines the renderer drew, and candidate
positions around each. The cost of a placement is what is wrong with it: ink under the character,
the character inside another part's outline, a lead line across another part, a lead line crossing
another lead line. Most-constrained numerals go first, then the worst-placed one is moved
repeatedly until nothing improves. It is deterministic: the same figure gives the same placement.

A numeral is allowed to sit inside a box that also contains the part it points at. That is a
subsystem's numeral inside the subsystem, which is how a real block diagram is drawn.

### 7. The checker (`fm/validate/`)

**No model is called here at all.** Two layers:

*Data.* Numerals in the drawings against the registry and back again; one character per part and
one part per character; consecutive figure numbering including letter suffixes; every independent
claim element depicted; hatching on sectional views; the brief description against the set.

*The sheet.* Margins and the sight (2.5 cm top and left, 1.5 cm right, 1.0 cm bottom, sight no
more than 17.0 x 26.2 cm); character height at least 0.32 cm; line weight and uniformity;
permitted text only; lead lines that touch what they point at and never cross; views not crowded
and each within its sheet. Then the sheet is rasterised at 300 dpi and checked for colour, for
grey that is tone rather than the soft edge of a black line, for stray ink in the margin, and for
hairlines. If the rasteriser is missing it **says so as a finding** rather than passing quietly.

Every finding carries a citation and a **basis**: `rule` where the wording is the Office's,
`practice` where the regulation states a requirement without a number and this is the threshold
used to make it testable. Telling an attorney that a drawing violates 37 CFR 1.84(l) when what
happened is that it failed somebody's threshold is how a compliance report stops being trusted.

Findings name the stage that caused them, which is what the retry loop routes on: a missing
element goes back to the planner with the element quoted, an unbuildable scene goes back to the
scene call for that one figure, a crossed lead line goes back to the solver with more room. The
budget is small and fixed. A draft that still fails has something wrong with it that another model
call will not fix, and the report says what.

### 8. Editor and export (`app.py`, `fm/export.py`, `fm/redline.py`)

Figure beside registry. Drag a numeral; drag the end of a lead line to point it elsewhere on the
same part; edit a term. Every edit re-runs the whole check.

Out: SVG sheets in real millimetres, a PDF (vector, never rasterised on the way out), a zip of
everything, and a redline of the specification with the proposed brief description and the
reference characters that would be added.

## Evaluation

```
./.venv/bin/python -m evalkit.run --limit 5
./.venv/bin/python -m evalkit.officeactions
```

A granted patent is a labelled example: a specification went in and a figure set an examiner
accepted came out. What it does not give you is the drawings as data, so the ground truth is what
the document states about its own figures, all of which is text: which views exist and what each
one is, which characters exist, and which characters belong to which view.

Four measures, each failing for a different reason: numeral-set agreement, per-figure agreement,
claim-element coverage, and validator pass rate. What is deliberately **not** measured is whether
the picture resembles the applicant's picture; two draughtspeople given one specification draw
different pictures, and scoring against pixels would reward imitation.

### The first run, six granted patents

```
patent               figs  numerals  per-fig   claims  kind   err   warn   secs
US10000000B2          7/7     0.961    0.542    0.405  1.00     3     53    287
US10102449B1        12/50     0.241    0.092    0.593  1.00   108     18    638
US10195470B2          7/7     0.613    0.287    0.282  1.00    54     66   1244
US10583560B1          6/6     0.625    0.263    0.673  1.00    53     31    959
US10717208B1        12/18     0.570    0.347    0.724  1.00    72     26   2040
US11000000B2          3/3     0.923    0.970    0.375  1.00     3      9    508

numeral agreement 0.655   per-figure 0.417   claim coverage 0.509
figure labels 0.818       kind agreement 1.000    validator pass rate 0.000
```

Read it in this order.

**Kind agreement is 1.000.** Every view came out the type the applicant's own brief description
says it is: block diagram, flow chart, perspective, section. The planner is reading the draft
rather than guessing.

**Nothing is ever invented.** Across all six cases the count of numerals drawn that the
description does not mention is zero. 37 CFR 1.84(p)(4) has two directions and this one is clean.

**Every failure is an omission, and it is always reported.** 182 of the 271 errors are
`registry_numeral_undrawn`: a numeral the description mentions that reached no view. On a draft
with a moderate numeral count that barely happens (US11000000B2, 13 numerals: one missing;
US10000000B2, 51 numerals: two). On a draft with 80 to 111 numerals the planner places about two
thirds of them and the checker says so for each of the rest. It does not quietly draw a smaller
drawing set and call it done.

**The validator pass rate is 0.000, and that is the honest number.** No granted patent in this
corpus produced a set with no errors left. The rate is the measure that will move as the planner
improves, and reporting anything else would mean loosening the checks until they passed.

Two limits are visible in the table. `12/50` and `12/18` are the figure cap binding; this run was
made with it at 12, it is now 20, and when it binds the report says so first rather than leaving
dozens of downstream errors to explain themselves. And `US10195470B2` has one figure at exactly
18 elements, which is the per-figure cap: a view that dense wants splitting, which is what the
finding says.

What that says about where to work next: not on the geometry, which is clean, and not on the
checks, which caught all of this. On the planner's recall over drafts with a hundred numerals.

`evalkit/officeactions.py` mines real office actions from the USPTO Open Data Portal for
paragraphs objecting to the drawings and sorts them into the rules they invoke. That is used for
**coverage, not accuracy**: of the drawing objections examiners really write, which kinds could
this checker have caught? A class with no check behind it is named as a gap.

The first run of it, over 140 robotics applications filed 2016 to mid-2019:

```
287 office actions read, 24 drawing objections found, 28 classifications, 0 unclassified

  15  missing_claimed_feature        claim_element_not_depicted   37 CFR 1.83(a)
   5  margins_or_sheet               outside_margins              37 CFR 1.84(g)
   2  character_not_in_drawing       registry_numeral_undrawn     37 CFR 1.84(p)(4)
   2  character_size_or_legibility   numeral_too_small            37 CFR 1.84(p)(3)
   1  element_without_a_character    element_unnumbered           37 CFR 1.84(p)(4)
   1  line_quality                   line_too_thin                37 CFR 1.84(l)
   1  view_numbering                 figures_not_sequential       37 CFR 1.84(u)(1)
   1  shading_or_colour              shading_present              37 CFR 1.84(m)
```

Every class that appeared has a check behind it, and the one that dominates by a factor of three
is 37 CFR 1.83(a), the drawing showing every feature the claims specify. That is the check this
pipeline is built around, and it is the reason the registry and the claim split exist at all.

Two things had to be got right before that number meant anything. The Office's own PDF of an
office action is a scan, and pypdf gets six characters out of a seven-page rejection, so the
first run reported no objections anywhere; the text is in the XML and MS_WORD options the same
response already offers. And the classifier originally matched only the wording of the
regulation, which left every objection saying "reference number ... not labeled" in the
unclassified pile, all of them instances of a check that already existed.

## Running it

```
./run.sh                                          # gunicorn on :8639
./.venv/bin/python fmrun.py US11000000B2 --out /tmp/run   # one draft, from a terminal
./.venv/bin/python -m tests.smoke /tmp/fm-smoke           # every renderer, no model
./.venv/bin/python -m pytest tests/ -q --ignore=tests/smoke.py
```

Needs `graphviz` (`apt-get install -y graphviz`) for block diagrams and flow charts, and
`cairosvg` plus `pypdf` for the raster checks and the PDF. Each reports itself by name if absent.

Models are reached over Vertex AI as the VM's own service account, so there is no key to rotate
into this app. `FM_FAST_MODEL` reads the draft, `FM_DEEP_MODEL` decides what the figures are.

Budget roughly a minute per figure: the deep model is left free to think, and figures are rendered
in order because each one constrains the next. A replan reuses the scenes of figures it did not
change.

## Deployment

Host `nimo-iptorch-patents`, `~/patent-figures-maker/figuresmaker`, port 8639, supervisor program
`figuresmaker`, nginx `location ^~ /figuresmaker/` in `nimo-iptorch.conf`.

Sign-in is the search app's, at `https://nimo.iptorch.com/login`. This app has no password of its
own: a second credential for the same person on the same domain is a thing to lose, not a security
measure. `authgate.py` verifies the pilot's signed cookie with the pilot's key, then checks
`app_users.is_active` and `session_version`, and **fails closed** if Postgres cannot be reached.

> **Install with `supervisorctl reread` then `add figuresmaker`.** Never `supervisorctl update`
> and never `restart all` on this host: both bounce `patent-results` and kill whatever prior-art
> search is running. A config change needs `stop`, `remove`, `reread`, `add` for this program
> alone. Restarting `figuresmaker` on its own is safe; a job it was running dies with it and says
> so when the browser next polls.
